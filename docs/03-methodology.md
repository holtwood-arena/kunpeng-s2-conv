# 性能工程方法论

> 这个项目要交付的不是「一个更快的 kernel」，而是**一套可复用的性能优化工作流**，
> 以及它在一个真实算子上的完整实施记录。

## 0. 一句话概括

> 性能优化不是「改代码直到变快」，而是**在约束下做受控实验**：
> 先建立可信测量，再用证据定位瓶颈，然后用可证伪的假设驱动改动，最后用数据决定保留还是回滚。

## 1. 为什么大多数「优化」讲不清楚

常见的失败叙事：

- 「我加了 SIMD，快了 3 倍」——但说不出为什么原来慢、为什么快 3 倍而不是 8 倍
- 「我做了 cache 分块」——但说不出分块尺寸怎么定的、换一个尺寸会怎样
- 「我调了编译选项」——但这不叫优化，叫碰运气

它们的共同问题：**没有可证伪的假设，也没有把改动和结果之间的因果链闭合。**

面试官只要问三层就会穿：

1. 你怎么知道瓶颈在这？
2. 你怎么知道是你的改动带来的收益？
3. 如果换个尺寸，还成立吗？

## 2. 四层证据（缺一层就会被追问穿）

| 层 | 手段 | 回答什么问题 | 成本 |
|---|---|---|---|
| L1 解析 | 算术强度、roofline、复杂度分析 | **理论上**瓶颈该在哪 | 纸笔，几分钟 |
| L2 编译 | `-fopt-info-vec`、`-S` 看汇编 | 编译器**实际**生成了什么 | 分钟级 |
| L3 硬件 | `perf stat`（IPC / cache-miss / stalled-cycles） | 硬件**实际**卡在哪 | 需要权限与复现 |
| L4 端到端 | 多次计时、min/median/max | 最终是否真的变快 | 分钟到小时 |

本项目的规矩：

- **先 L1 再动手**。算完算术强度就知道该不该往访存方向使劲。本题是 1615 FLOP/Byte 的纯 compute-bound，所以「减少内存访问」这条路的理论天花板很低——这一步就能砍掉一半无效尝试。
- **L2 是必做项**，因为它便宜且确定性高。编译器报告里出现 "not vectorized: possible dependence"，比任何猜测都可靠。
- **L3 有条件就做，没条件就明说**。WSL2 里 `perf` 常常不可用，那就写「未采集」，而不是编一个数字。
- **L4 是唯一能对外声称的结果**，但它最容易被噪声污染，所以必须有协议（见 `04-experiment-protocol.md`）。

## 3. 假设—实验闭环

每个改动必须写成一条**可证伪的假设**，而不是一句「优化一下」。

模板：

```
假设 Hk：
  当前实现中，<某个具体机制> 导致了 <某个可观测的浪费>。
  因此，<改动> 应当使 <指标> 改善，且 <反证条件> 不出现。

预测：
  GFLOPS 提升 ≥ X%；或某计数器下降 ≥ Y%。

证伪条件：
  若 GFLOPS 变化落在噪声带内，或 <反证条件> 出现，则假设不成立。
```

举例（本项目第一条）：

```
假设 H1：
  内层 output[...] += input*kernel 是 read-modify-write，
  且三个裸指针之间缺少别名信息，编译器无法把 output 提升到寄存器。
  因此改成局部累加器后，循环体内应不再出现对 output 的 load/store。

预测：
  四案 GFLOPS 提升 10%~40%；汇编中内层循环对输出地址的访存指令消失。

证伪条件：
  若汇编中输出访存仍在（说明编译器本就能优化），或 GFLOPS 落在噪声带内，则 H1 不成立。
```

这样做的好处：

- **失败也是产出**。假设被证伪，你得到一条确定的知识边界，而不是一次白忙。
- **面试可讲**。你可以完整复述"我当时怎么想的、怎么验证的、结果如何"。
- **防止自我欺骗**。先写证伪条件，就不会事后把噪声解释成收益。

## 4. 取舍必须显式记录

每个优化都有代价。本项目要求每保留一个改动，同时记录它的**代价项**：

| 维度 | 典型代价 |
|---|---|
| 正确性 | SIMD 改变归约顺序 → FP32 误差累积路径改变 → 可能撞 1e-5 |
| 复杂度 | 分块引入尾块路径，核尺寸 39/41/55/81 全是奇数，边界代码量翻倍 |
| 可移植性 | 手写 intrinsics 绑定向量宽度；换架构要重写 |
| 可维护性 | 特化分支越多，后续改动越容易漏 |
| 可验证性 | 特化后必须保证每条分支都被 4 案覆盖 |

没有代价记录的优化，在面试里会被当成「抄来的」。

## 5. 停止条件（比优化本身更重要）

三条硬止损线，任一触发就停：

1. **收益 < 噪声**：连续 3 次测量的抖动大于改动带来的差异 → 这个改动不可证明，放弃
2. **精度逼近门限**：最大绝对误差从 `0.0` 升到 `>1e-6` → 停止加码，回到上一版
3. **复杂度收益比失衡**：为 <5% 收益新增 >50 行特化代码 → 不值

第 3 条尤其重要。真实工程里，「不做」往往比「做了」更需要判断力，而这一点恰恰是面试官爱问的。

## 6. 这个项目刻意不做的事

明确写出来，是为了让边界清晰：

| 不做 | 原因 |
|---|---|
| SME 矩阵扩展 / 手写汇编 | 头部获奖方案走了这条路（9k~33k 行），但它绑定 920F 的 SVE/SME + HBM，无法在通用环境验证；且讲不清原理的硬件特化在面试中是负资产 |
| 针对四案尺寸硬编码 | 那是刷榜手段，不是工程能力 |
| 无测量的调参 | 编译选项扫描可以有，但必须作为「实验」记录，不能作为「成果」 |
| 把 x86 数据当成鲲鹏数据 | 架构不同，峰值与缓存层级都不同 |

## 7. 最终交付物（面试时拿得出手的东西）

1. **一份方法论**（本文档）——证明你知道怎么做，而不只是做过
2. **一套实验协议**（`04-experiment-protocol.md`）——证明你的数据可信
3. **一条完整的证据链**——某个假设从提出到验证/证伪的全过程
4. **一张对比表**——baseline 到 final 的每一步收益与代价
5. **至少 3 条负面结果**——证明你真的试过，而不是照着教程抄
6. **可复现的脚本**——别人能重跑

这六样齐了，项目就算完成，**与最终 GFLOPS 是多少无关**。
