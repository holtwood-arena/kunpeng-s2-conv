# 面试逐字稿与简历条目

> 直接可背的版本。数字位置用 `【】` 标出，实测后替换。

## 一、3 分钟逐字稿

> 我这个项目是把一个 30 行的朴素二维卷积，在 ARM 平台上做性能优化。
>
> **先说问题。** 这是鲲鹏 HPC 挑战赛 S2 的赛题，FP32 单通道卷积，四组用例最大 6390×4256、卷积核 81×81，单次计算 345 GFLOP。官方基线是四重循环，只加了一句 `#pragma omp parallel for`。
>
> **我的第一步不是改代码，是算。** 我算了算术强度：345 GFLOP 除以约 214 MB 访存，大约 1615 FLOP/Byte。这个数字远高于任何 CPU 的 roofline 拐点，说明它是纯计算瓶颈。所以「减少内存访问」这条路天花板很低，力气应该放在指令级并行上。这一步让我砍掉了一半无效方向。
>
> **第二步是定位。** 读基线代码，内层是 `output[...] += input * kernel`。三个问题：输出是 read-modify-write，每个 MAC 都要读写一次输出；地址在整个内层循环里不变，本可以放寄存器；但三个裸指针没有 `restrict`，编译器必须假设它们可能重叠，所以不敢提升。
>
> **第三步是验证。** 我把它改成局部累加器，循环结束写一次，同时删掉冗余的 memset。但改之前我先写了证伪条件：如果反汇编里内层还有对输出的访存，或者性能变化落在噪声带内，就说明假设不成立。
>
> **第四步是测量纪律。** 每次至少三次重复，报 min / median / max，抖动超过 5% 就先修测量。改动收益如果小于抖动，我判它无效，不写成「有提升」。
>
> **还有一个我特意做的实验。** 我设计了一个「预期失败」的对照：用行指针替代二维下标。直觉上应该更快，但公开项目实测四组用例全部变慢 2.6% 到 5.7%。因为现代编译器早就做完了强度削减。这个失败让我后面的判断更保守，也更有依据。
>
> **边界我也说清楚。** 我没有走 SME 矩阵扩展那条路。头部获奖方案用了它，代码九千到三万行，绑定 920F 的 SVE/SME 和 HBM，无法在通用环境验证。我选择的是可解释、可复现的通用优化路径。
>
> 如果要一句话总结：我做的不只是让卷积变快，而是建立了一条从测量、定位、假设、验证到取舍的完整证据链。

## 二、60 秒压缩版

> 我优化了一个 FP32 二维卷积。四组官方用例，最大单次 345 GFLOP。
>
> 我没有直接改代码，先算了算术强度——1615 FLOP/Byte，纯计算瓶颈，所以排除了「优化访存」这个大方向。
>
> 然后读基线，定位到内层 `output += ` 是 read-modify-write，加上裸指针没法做别名分析，输出提不到寄存器。我改成局部累加器，并先写好证伪条件再动手。
>
> 测量上我要求三次重复、报中位数，收益小于抖动就判无效。
>
> 我还特意做了一个预期失败的对照实验，用行指针替代二维下标，结果确实慢了 3%~6%——这让我对「凭直觉猜优化点」这件事更警惕。
>
> 最后我没走 SME 汇编那条路，因为它不可复现也讲不清原理。我的价值在于完整的证据链，不是绝对名次。

## 四、开场与收尾

**开场（15 秒）**：

> 我准备了一个算子优化的项目，重点不是性能数字，而是我怎么做性能优化的完整流程。

先说这句话，面试官会知道你要讲方法论，不会一上来就追着问「快了百分之多少」。

**收尾（20 秒）**：

> 这个项目我刻意没做两件事：一是没走 SME 汇编那条路，因为它在通用环境无法验证，讲了也证明不了；二是没针对四组尺寸硬编码，那是刷榜不是工程。我想证明的是我能在一个新问题上快速建立可信的优化流程。
