# 面试逐字稿与简历条目

> 直接可背的版本。数字位置用 `【】` 标出，实测后替换。

## 一、3 分钟逐字稿

> 我这个项目是把一个 30 行的朴素二维卷积，在 ARM 平台上做性能优化。
>
> **先说问题。** 这是鲲鹏 HPC 挑战赛 S2 的赛题，FP32 单通道卷积，四组用例最大 6390×4256、卷积核 81×81，单次计算 345 GFLOP。官方基线是四重循环，只加了一句 `#pragma omp parallel for`。
>
> **我的第一步不是改代码，是算。** 我算了算术强度：345 GFLOP 除以约 214 MB 访存，大约 1615 FLOP/Byte。这远高于任何 CPU 的 roofline 拐点，说明它是纯计算瓶颈。所以「减少内存访问」这条路天花板很低，力气应该放在指令级并行上。这一步砍掉了一半无效方向。
>
> **第二步是定位。** 读基线代码，内层是 `output[...] += input * kernel`。三个问题：输出是 read-modify-write，每个 MAC 都要读写一次输出；地址在整个内层循环里不变，本可以放寄存器；但三个裸指针没有 `restrict`，编译器必须假设它们可能重叠，所以不敢提升。
>
> **第三步是改，然后被打脸。** 我把它改成局部累加器，循环结束写一次，删掉冗余 memset。按源码看累加顺序一个字没变，所以我预测误差还是 0。结果实测：小规模 2.86e-06，官方大核用例 1.22e-04，直接超出 1e-5 容差，FAIL。
>
> **我去查了根因。** 反汇编对比：原版内层是 `vmulss` 加 `vaddss`，新版出现了 `vfmadd`。也就是说编译器把寄存器里的 `sum += a*b` 收缩成了 FMA 指令，中间结果不再经过 FP32 舍入。我加上 `-ffp-contract=off` 重编，误差精确回到 `0.00e+00`。
>
> **这件事让我明白：决定精度的不是源码语义，是编译器实际生成的指令。** 而且如果我只测 512×512 的小规模，误差 2.86e-06 是能过的——就会误判为通过。必须用官方四案回归。
>
> **性能上分两级。** 第一级局部累加器，四组用例中位数提升 7.9% 到 10.7%。第二级做输出分块——一次并行累加 4 个相邻输出，核系数加载一次复用四次，又提升约 3 倍。累计从 13.6 到 45 GFLOPS，峰值占比从 5% 到 15%。
>
> **后面两步我都做失败了。** 加 `__restrict` 让编译器报告「loop vectorized」，实测反而慢 3%；把 4 路加到 8 路，慢 19%。这两次失败比成功更能说明问题：**编译器说向量化了，不等于真有收益；加宽也不是免费的。**
>
> **边界我也说清楚。** 我没有走 SME 矩阵扩展那条路。头部获奖方案用了它，代码九千到三万行，绑定 920F 的 SVE/SME 和 HBM，通用环境验证不了，也讲不清每一行为什么这么写。
>
> 一句话总结：这个项目最有价值的不是那 9% 的提速，而是我发现了一个只靠读代码绝对发现不了的坑。

## 二、60 秒压缩版

> 我优化了一个 FP32 二维卷积。四组官方用例，最大单次 345 GFLOP。
>
> 我没有直接改代码，先算算术强度——1615 FLOP/Byte，纯计算瓶颈，所以排除了「优化访存」这个大方向。
>
> 然后定位到内层 `output += ` 是 read-modify-write，加上裸指针没法做别名分析，输出提不到寄存器。我改成局部累加器。
>
> 改完我发现了一个只读代码发现不了的问题：源码累加顺序没变，但编译器把它收缩成了 FMA 指令，误差从 0 变成 1.22e-04，直接超出容差。关掉 FMA 收缩后误差精确回到 0。
>
> 之后我又做了输出分块，一次算 4 个输出，把核系数复用起来，性能从 15 涨到 45 GFLOPS。
> 累计是 3.3 倍，峰值占比从 5% 到 15%。
>
> 我没走 SME 汇编那条路，因为它不可复现也讲不清原理。我的价值在于完整的证据链，不是绝对名次。
