# E01 局部累加器 + 删除冗余 memset

- 日期：2026-11-05（记录建立）
- 状态：**已实测（2026-11-05）**
- 上一版：`src/conv2d_v0.c`
  - SHA-256 `bb34cc60053b74a928ba15519015d1ff3b89ba67cc462048d38e916ffcf08961`
- 本版：`src/conv2d_v1.c`
  - SHA-256 `485cdb222b5a7f253e1a4c6585e8e3ee58a2e165b5bfae24414103e76f54ba74`
  - 二进制变体：`v1`（默认，含 FMA 收缩）、`v1_nocontract`（`-ffp-contract=off`）
- 环境（LOCAL_REFERENCE）：
  - CPU：AMD Ryzen 7 5800H，6 物理核 / 12 逻辑核，单 NUMA
  - 编译器：gcc 13.3.0，`-O3 -fopenmp -march=native`
  - 线程：`OMP_NUM_THREADS=6`（物理核数，不绑核）
  - 内存：17 GB，可用约 10 GB

## 1. 观察（动手前的证据）

`src/conv2d_v0.c` 第 25 行：

```c
output[j * outputWidth + i] += input[inputIdx] * kernel[kernelIdx];
```

这一行在**最内层**，用例 4 每次输出要执行 6561 次。三次可疑：

1. `output[...]` 出现在赋值左侧且是 `+=`，语义等价于
   `load → fma → store`，每个 MAC 都有一次输出访存。
2. 地址 `j*outputWidth + i` 在这 6561 次内**完全不变**，
   本可以被提升到寄存器。
3. 但 `input` / `kernel` / `output` 都是**裸指针**且无 `restrict`，
   编译器必须假设三者可能重叠 —— 写 `output` 可能改变 `input` 的值，
   因此无法把输出提升出循环（别名阻碍）。

旁证（L1，解析层）：`src/conv2d_v0.c` 第 17 行对整个输出调了 `memset`。
若每个输出元素最终都会被完整覆盖一次，这次清零就是纯浪费 ——
用例 4 下等于额外写 105 MB。

## 2. 假设

> 内层的 `output += ` 是 read-modify-write，且受裸指针别名阻碍无法寄存器提升；
> 同时 `memset` 是冗余的。

## 3. 预测

- **性能**：四案 GFLOPS 中位数提升 **10% ~ 40%**
- **代码**：内层循环体内对输出地址的 `load`/`store` 消失，
  只剩循环外的一次写入
- **正确性**：最大绝对误差仍为 `0.00e+00`（累加顺序未变）

## 4. 证伪条件

满足任一即判假设不成立：

1. 反汇编中内层循环**仍存在**对输出地址的访存指令
   （说明编译器原本就能优化，收益来源另有其因）
2. 四案 GFLOPS 变化全部落在噪声带内（< 2× 抖动）
3. 任一用例正确性 FAIL
4. 最大绝对误差从 `0.00e+00` 变为非零

## 5. 改动说明

**单变量原则的例外说明**：本实验实际包含两处改动——

| 改动 | 内容 | 是否必须与本实验绑定 |
|---|---|---|
| ① | 局部 `float sum` 累加，循环结束写一次 | 核心改动 |
| ② | 删除 `memset` | **②是①的必然推论**，不可分割 |

理由：`memset` 之所以存在，是因为原实现用 `+=` 需要初值。
一旦改为局部累加，清零就失去意义。若强行拆成两个实验，
"保留 memset 的局部累加版"只是为了测一个已知冗余的开销，信息量很低。

### ② 的正确性论证

对任意 `(j, i) ∈ [0, OH) × [0, OW)`：

- 内层循环结束后执行 `output[j*OW + i] = sum;`，**恰好一次**
- `j*OW + i` 在 `j ∈ [0,OH)`、`i ∈ [0,OW)` 上**双射**到 `[0, OH*OW)`
- 故每个输出元素恰被赋值一次，无需初值

前提：`OH > 0 且 OW > 0`（即 `inputHeight ≥ kernelHeight` 且 `inputWidth ≥ kernelWidth`），
由赛题用例保证（4096×6144 起，核最大 81）。

**附带改进**：原 `memset(output, 0, OH*OW*sizeof(float))` 在 `OH*OW < 0` 时，
`size_t` 转换会产生极大值（未定义行为，实测会段错误）。删除后此路径变为"不写"，
对非法输入反而更安全。

## 8. 汇编检查（证伪条件 1）

```bash
gcc -O3 -fopenmp -march=native -S -o v0.s src/conv2d_v0.c
gcc -O3 -fopenmp -march=native -S -o v1.s src/conv2d_v1.c
gcc -O3 -fopenmp -march=native -ffp-contract=off -S -o v1_nc.s src/conv2d_v1.c
```

| 文件 | `vfmadd` | `vmulss` | `vaddss` |
|---|---:|---:|---:|
| v0 | **0** | 1 | 1 |
| v1 | **3** | 0 | 12 |
| v1_nocontract | **0** | 3 | 15 |

**结论**：

- `v0` 内层是 `vmulss` + `vaddss`，**没有** FMA —— 因为输出是 memory RMW，
  编译器不敢把它收缩成 `vfmadd`
- `v1` 内层出现 `vfmadd` —— 累加器进了寄存器，正好匹配 FMA 模式，
  GCC 默认 `-ffp-contract=fast` 就把它收缩了
- `v1_nocontract` 回到 `vmulss` + `vaddss`

**这就是误差的来源。**

FMA 把 `a*b` 与 `+` 合并成一条指令，中间结果不经过 FP32 舍入。
数学上更精确，但**与参考实现的「先乘后加」结果不同**。
容差 1e-5 对 1521～6561 项累加并不宽松，误差累积到 1.22e-04，直接翻倍超标。

### 这条为什么重要

源码的累加顺序**一个字都没改**，只是把累加器从内存挪到寄存器，
精度却从 `0.00e+00` 变成 `1.22e-04`。

**决定精度的不是源码语义，是编译器实际生成的指令。**

## 9. 判决

- 结果：**KEEP（附强制条件）**
- 条件：交付版本必须用 `-ffp-contract=off` 编译，或改用显式 `fmaf` 之外的两步写法

| 预测 | 实测 | 判定 |
|---|---|---|
| 提升 10%~40% | +7.90% ~ +10.74% | **略低于预测下沿**，方向正确 |
| 内层输出访存消失 | `vfmadd` 出现，输出访存确实消失 | ✅ 成立 |
| 误差保持 0 | 默认编译 FAIL（1.22e-04） | ❌ **被证伪** |

- 理由：性能有确定的 +8%~+11% 正收益，且远大于噪声；
  但默认编译下精度不可用，必须显式关闭 FMA 收缩。
- **代价**：
  - 正确性：默认编译会破坏 1e-5 容差，**必须** `-ffp-contract=off`
  - 性能：关闭 FMA 收缩会损失一部分本可获得的收益（具体数值未测，
    因为默认版本在精度检查阶段就被拦截，没能进入性能测试）
  - 复杂度：无
  - 可移植性：`-ffp-contract` 是 GCC/Clang 通用选项，但默认值可能随版本变化
