# E12 输出维度向量化（本项目最大的一次收益）

- 日期：2026-11-05
- 上一版：`src/conv2d_v3.c`（E04，KEEP，此前最优）
- 本版：`src/conv2d_v7.c`
- 编译：`gcc -O3 -fopenmp -march=native -ffp-contract=off`
- 环境：`LOCAL_REFERENCE` — Ryzen 7 5800H（6C/12T），`OMP_NUM_THREADS=6`，`taskset -c 0-5`

## 1. 触发：一个自相矛盾的数字

E08 之后，我为了补齐「四层证据」里的硬件层，第一次对 v3 跑 `perf stat`：

| 指标 | v3 |
|---|---:|
| cycles | 2.37e11 |
| instructions | 5.54e11 |
| IPC | 2.34 |
| cache-misses | 30.97% |

IPC 2.34 在 Zen3 上不算低。但把它和 GFLOPS 放在一起算，就出问题了：

```
v3 约 44 GFLOPS = 每周期约 1.9 FLOP
Zen3 单核 256-bit 双发射理论约 16~32 FLOP/周期
```

**IPC 不低，但每周期的有效浮点运算极少。** 这说明大量指令不是在做计算。

这直接推翻了我此前的一个默认假设：我以为「4 路分块 + 编译器自动向量化」已经在用 SIMD 了。

## 2. 证据：编译器向量化错了维度

反汇编 v3 的内层主循环：

```asm
vmovups (%r11,%rax,1),%ymm2          ; 取 8 个 kernel 系数
vmulps  (%rdx,%rax,1),%ymm2,%ymm3    ; 窗口 A × k
vmulps  (%r10,%rax,1),%ymm2,%ymm6    ; 窗口 B × k
vmulps  (%r9,%rax,1),%ymm2,%ymm4     ; 窗口 C × k
vmulps  (%r8,%rax,1),%ymm2,%ymm2     ; 窗口 D × k
vunpcklps / vshufps / vmovlhps ...   ; 大量交错指令
vextractf128 $0x1,%ymm4,%xmm4
vaddps  %xmm1,%xmm0,%xmm0           ; 累加退回 128-bit / 标量
```

结论很明确：GCC 把内层 `ik` 循环**沿归约维度向量化**了。
它一次算 8 个 `ik` 的乘积，但那是"同一个输出的 8 个部分和"，
所以必须再做一次**水平归约**（把 8 个 lane 加起来）。

更糟的是，4 个相邻输出的滑动窗口互相重叠 5 个元素，
编译器还要用 `vunpcklps` / `vshufps` 把 4 组重叠窗口对齐后再合并。

**一次乘法的活，配了五六条洗牌指令。** 这就是每周期只有 1.9 FLOP 的原因。

## 3. 假设

> 把向量化维度从「归约维度 `ik`」换成「输出维度 `i`」：
> 让 8 个**不同输出**共享同一条向量累加器，就不需要任何交错与水平归约。
> 而且每个 lane 对应一个独立输出，其 `jk → ik` 累加顺序与标量版本逐位一致，
> 所以精度应当仍然是 0 误差。

这一条很关键：**它不违反 E09 得出的容差约束**。
E09 证明的是「不能改变单个输出的累加顺序」，
而这里每个输出的累加顺序一点没变，变的是「同时算几个互不相干的输出」。

## 4. 实现

不写 intrinsics，用可移植的写法让编译器自己选宽度：

```c
CONVFLOAT sum[VB] = {0};                    // VB = 8，8 个独立输出
for (jk) {
    for (ik) {
        const CONVFLOAT kv = k_row[ik];
#pragma omp simd
        for (int t = 0; t < VB; ++t) {
            sum[t] += in_row[i + ik + t] * kv;   // lane t 恒对应输出 i+t
        }
    }
}
for (int t = 0; t < VB; ++t) out_row[i + t] = sum[t];
```

`#pragma omp simd` 在这里的作用不是"让它向量化"（编译器本来就会），
而是**告诉编译器沿 `t` 维度向量化是安全的**，从而抢在它自作主张选 `ik` 之前定下维度。

生成的代码正是想要的形态：

```asm
vbroadcastss (%r9,%r12,1),%ymm0      ; kv 广播到 8 lane
vmulps  (%rdi,%r12,1),%ymm0,%ymm0    ; 8 个输出 × kv
vaddps  %ymm0,%ymm1,%ymm1            ; 累加器保持在 ymm，无水平归约
```

`ymm1` 全程不落地，循环结束才写回一次。

## 5. 正确性

| 用例 | 结果 | 最大绝对误差 |
|---|---|---|
| 1（4096×6144 k39） | PASS | 0.00e+00 |
| 2（6144×4096 k41） | PASS | 0.00e+00 |
| 3（4256×6390 k55） | PASS | 0.00e+00 |
| 4（6390×4256 k81） | PASS | 0.00e+00 |

四案误差全部为 **0.00e+00**，与 v0 参考实现逐位相同。
这验证了第 3 节的判断：只并行独立输出、不改任何单条累加链，精度不受影响。

| 1（4096×6144 k39） | 43.4289 | **111.3726** | **×2.56** |

## 7. 硬件计数器验证（隔离单次调用）

`bench_conv.c` 含预热、参考实现和校验，perf 统计会混入无关代码。
因此新增 `tools/perf_probe.c`，只调用一次 `conv2d`：

| 版本 | cycles | instructions | IPC | FLOP/cycle |
|---|---:|---:|---:|---:|
| v1 | 1.127e11 | 1.515e11 | 1.34 | 0.67 |
| v3 | 3.632e10 | 9.384e10 | 2.58 | 2.08 |
| v7 | **1.515e10** | **3.018e10** | 1.99 | **5.00** |

（case 1，7.57e10 FLOP，6 线程绑定 0-5，三次 checksum 完全一致）

读法：

- **cycles 降 58%**：同样的 FLOP，实际耗时大幅下降
- **instructions 降 68%**：洗牌与交错指令基本消失
- **IPC 从 2.58 降到 1.99**：这是**好事**。IPC 高说明每周期塞了很多指令，
  但那些指令大多是 `vshufps`；现在指令少了、每条更"值钱"
- **FLOP/cycle 从 2.08 升到 5.00**：这才是真实效率

这一条正好回答了一个常见的面试陷阱：**IPC 高不等于性能好。**
要看的不是"每周期执行多少条指令"，而是"每周期完成多少有用的工作"。

## 8. 与 E07 的对照：同样是 8 路，结果相反

E07 也做 8 路，结果是 **−19.2%**；E12 也是 8 路，结果是 **+150%**。
差别不在"几路"，而在**让编译器沿哪个维度向量化**：

| | E07（v4） | E12（v7） |
|---|---|---|
| 写法 | 8 个标量变量手工展开 | 8 元素数组 + `omp simd` |
| 编译器选择 | 仍沿 `ik` 归约维度向量化 | 沿 `t` 输出维度向量化 |
| 归约开销 | 8 组水平归约，寄存器压力爆掉 | 无水平归约 |
| 结果 | −19.2% | **+150%** |

**优化的不是我写了什么结构，而是我让编译器生成了什么指令。**

## 9. 判决

- 结果：**KEEP**
- 理由：四案一致 ×2.47~2.56，误差 0，硬件计数器方向一致（cycles/instructions 双降）
- **代价**：
  - `VB=8` 绑定 256-bit 向量宽度。鲲鹏 NEON 是 128-bit（4×FP32），
    需要把 `VB` 调成 4 或让编译器自动切分；**x86 的倍数不能外推到 ARM**
  - 尾块仍需标量路径（核宽 39/41/55/81 全为奇数，`OW` 也不保证整除 8）
  - 仍依赖 `-ffp-contract=off`：一旦允许 FMA 收缩，误差立刻不再是 0

## 10. 它修正了什么

- **E09 的结论需要收窄**：1e-5 容差禁止的是「改变单个输出的累加顺序」，
  不是「禁止并行」。E12 在完全不动累加顺序的前提下又拿了 2.5 倍。
- **E04 不是终点**：v3 的 4 路分块确实有用（×3.3），但它把编译器引向了错误的向量化维度，
  导致后续收益被归约开销吃掉。**一个有效的优化，可能同时埋下一个更深的坑。**
