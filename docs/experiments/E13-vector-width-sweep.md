# E13 向量宽度扫描：修正 E12 的错误归因

- 日期：2026-11-05
- 触发：对 E12 结论的自我复查
- 基线版本：`src/conv2d_v3.c`（E04，4 路标量分块）
- 对照版本：`src/conv2d_v7.c`（VB=8）、`src/conv2d_v8.c`（VB=32）、`src/conv2d_v9.c`（VB=64）
- 编译：`gcc -O3 -fopenmp -march=native -ffp-contract=off`
- 环境：`LOCAL_REFERENCE` — Ryzen 7 5800H（6C/12T），`OMP_NUM_THREADS=6`，`taskset -c 0-5`

## 1. 为什么要做这个实验

E12 得出的结论是：

> ×2.5 来自「把向量化维度从归约改成输出」。

写完就被质疑：**v3 是 4 路，v7 是 8 路，两个变量同时变了。**
如果收益其实来自「路数」而不是「维度」，那 E12 的归因就是错的。

这个质疑是对的。整个 E12 缺少最基础的单变量隔离。

## 2. 扫描结果

只改 `VB` 常量，其余代码逐字节相同（`src/conv2d_v8.c` / `v9.c` 由 v7 直接替换常量生成）。

case 1（4096×6144，k=39×39），单次：

| VB | GFLOPS | 相对 v3 |
|---:|---:|---:|
| 2 | 22.83 | ×0.53 |
| **4** | **12.79** | **×0.30** |
| 8 | 95.52 | ×2.23 |
| 16 | 152.46 | ×3.56 |
| 32 | 209.05 | ×4.89 |
| **64** | **273.84** | **×6.40** |
| 128 | 197.53 | ×4.62 |

（v3 = 42.78）

两个现象直接推翻了 E12 的单一归因：

1. **VB=4 崩塌**，比 VB=2 还慢，比 v3 慢 3 倍多
2. **VB 从 8 涨到 64 又拿了 2.9 倍**，这段和「维度」毫无关系

## 3. 为什么 VB=4 会崩

反汇编 `v7`（VB=4）：

```
3   vmulps     16  vaddss
1   vaddps      6  vmulss
```

**它根本没被向量化。** 只有 3 条 `vmulps`，却有 16 条标量 `vaddss`。
`#pragma omp simd` 在 4 元素循环上被 GCC 的成本模型拒绝，
退化成标量，还额外背了循环结构的开销。

而 VB=8 时循环正好是 8 个 float = 一个 `ymm`，编译器才愿意生成 256-bit 向量代码。

对照实验确认了向量化的独立贡献：

| 配置 | GFLOPS |
|---|---:|
| 8 路 + `omp simd` | 95.52 |
| 8 路 + `-fno-tree-vectorize` | 61.36 |

## 4. 正确的因果链（三层，缺一不可）

E12 只讲了第 2 层。

| # | 因素 | 证据 |
|---|---|---|
| 1 | **向量宽度门槛**：lane 数必须 ≥ 硬件向量宽度（AVX2 为 8），否则编译器直接不向量化 | VB=4 汇编只有 3 条 `vmulps`，16 条 `vaddss` |
| 2 | **向量化维度**：沿输出维度向量化才不需要水平归约 | v3 的汇编有 `vunpcklps`/`vshufps`/`vextractf128` 做归约；v7 的累加器全程留在 `ymm` |
| 3 | **展开摊销**：VB 越大，每个 `(jk,ik)` 迭代摊掉的地址计算与循环控制越多 | VB 8→64 再拿 2.9 倍；这段收益与 SIMD 维度无关 |

第 3 条是 VB=64 的主要来源，E12 完全漏掉了。

## 5. 正式交错 A/B（四案 × 3 轮）

中位数（GFLOPS）：

| 用例 | v3 | VB=8 | VB=32 | VB=64 |
|---|---:|---:|---:|---:|
| 1（4096×6144 k39） | 44.4207 | 109.3569 | 228.8035 | **232.3160** |
| 2（6144×4096 k41） | 42.9481 | 110.5462 | 223.1865 | **257.2891** |
| 3（4256×6390 k55） | 45.0090 | 111.8610 | 271.4875 | **293.6717** |
| 4（6390×4256 k81） | 42.9853 | 106.4631 | 239.0657 | **263.9095** |

相对 v3：**×5.23 ~ ×6.53，中位 ×6.1**。

相对 v0 基线（13.51~14.01）：**×17 ~ ×21.6**。

抖动：VB=64 为 5.2%~8.6%，VB=32 为 6.0%~19.2%（case2 运行时间只有 330 ms，噪声占比高）。
VB=32 与 VB=64 在同一个平台区，差异大部分被噪声覆盖；取 VB=64 是因为四案中位都更高。

原始数据见 `bench/results/E13-20261105-x86.csv`（48 行）。

## 6. 硬件计数器（单次调用探针）

| 版本 | cycles | instructions | IPC | FLOP/cycle |
|---|---:|---:|---:|---:|
| v3 | 3.715e10 | 9.384e10 | 2.53 | 2.04 |
| v7（VB=8） | 1.499e10 | 3.018e10 | 2.01 | 5.05 |
| v9（VB=64） | **6.241e9** | **1.282e10** | 2.05 | **12.13** |

按 Zen3「2 条 256-bit FMA + 2 条 256-bit FADD，各 8 lane」估算，
上界约 32 FLOP/cycle，VB=64 达到约 **38%**。

注意：这个百分比依赖端口模型假设，**不是实测上界**。
此前 README 里写过的「31% / 16%」两个数字都建立在不牢靠的估算上，本次统一撤回，
只保留实测的 FLOP/cycle 绝对值。

## 7. 判决

- 结果：**KEEP（VB=64）**
- 理由：四案 5.2~6.5 倍，误差全部 `0.00e+00`，硬件计数器方向一致
- **代价与风险**：
  1. **VB=64 是 x86 特定结果**。ARM 只有 32 个 128-bit 向量寄存器，
     VB=64 需要 16 条 128-bit 累加器，寄存器严重不足，必须重新扫描
  2. **小尺寸退化**：当 `OW < 64` 时全部走标量尾块，性能会掉回 v1 水平。
     官方四案 `OW` 最小 4056，不受影响；但这不是通用实现
  3. 仍依赖 `-ffp-contract=off`

## 8. 这次错的教训

1. **对照实验必须只变一个变量。** 我把「4 路→8 路」和「归约维度→输出维度」捆在一起测，
   得到一个漂亮但错误的故事。
2. **参数不能只取一个点。** 如果当初做 8/16/32 扫描，立刻会看到单调上升，
   而不是把功劳归给「维度」。
3. **编译器行为有断崖。** VB=4 到 VB=8，性能差 7.5 倍，因为跨过了向量化门槛。
   这类非线性在调参时最容易被误读成「写法问题」。
4. **漂亮的解释最危险。** 「编译器选错了维度」这个说法自洽、好讲、有汇编支撑，
   所以我没再验证就写进了面试稿。**自洽不等于正确。**
